# UI Refactor Roadmap

本文档用于记录 Telegram Star 前端样式与交互分阶段重构的目标、范围、进度和验收标准。后续每次继续 UI 重构前，应先阅读本文档；每个阶段完成后，应同步更新进度与决策记录，避免目标在多轮迭代中丢失。

## 总目标

- 将现有界面重构为更现代、更高效的 Telegram 消息处理工作台。
- 保留现有业务行为与 API 兼容性，优先做最小、可验证、可回滚的阶段性改动。
- 提升高频路径体验：消息筛选、未读处理、原文跳转、过滤器维护、历史预览与拉取。
- 建立统一的视觉系统，减少零散样式、emoji 图标和重复交互模式。
- 保证桌面端与移动端都能稳定使用，尤其是消息页主从布局。

## 设计原则

- 工具优先：界面应服务于高频处理消息，而不是营销式展示。
- 信息密度可控：默认清晰，必要时支持更紧凑的消息浏览。
- 状态明确：未读、已读、停用、加载、错误、危险操作都应有一致反馈。
- 克制现代：使用干净背景、清晰边界、稳定布局和少量强调色，不依赖大面积渐变或装饰。
- 组件统一：优先使用现有 React、Tailwind、shadcn 风格组件和 `lucide-react` 图标。
- 响应式可靠：桌面端优先工作台布局，移动端优先单任务流程。
- 渐进重构：每个阶段都要保持可构建、可部署、可使用。

## 当前基线

- 前端技术栈：React + Vite + TypeScript + Tailwind CSS + shadcn 风格组件。
- 路由主入口包含消息、过滤器维护、通知设置、系统设置。
- 当前 `AppShell` 使用顶部 Tabs。
- 消息页已具备主从布局基础：
  - 桌面端：过滤器侧栏 + 消息列表。
  - 小屏：通过 `/messages` 与 `/messages/:filterId` 在列表和详情间切换。
- 消息卡片已支持媒体预览、已读切换、查看 Telegram 原文、搜索关键词高亮相关参数。
- 过滤器维护页已支持保存、删除、启停、预览、历史拉取。

## 阶段计划

### Phase 1: 设计 Token 与基础视觉系统

目标：

- 重整 `packages/web/src/index.css` 中的颜色、圆角、阴影、背景和状态色。
- 建立更稳定的应用级背景与卡片/面板层级。
- 明确主色、成功色、警告色、危险色、边框色、弱文本色的使用规则。
- 减少过强装饰性背景，保留必要的层次与焦点。

建议改动范围：

- `packages/web/src/index.css`
- 必要时微调基础 UI 组件：`packages/web/src/components/ui/*`

验收标准：

- `pnpm build` 通过。
- 现有页面无明显颜色冲突、文本不可读或状态不清。
- 未读、已读、禁用、错误、加载状态可以清楚区分。

状态：已完成

### Phase 2: AppShell 与全局导航

目标：

- 将顶部 Tabs 重构为更现代的工作台框架。
- 桌面端采用左侧导航 + 顶部状态区域 + 主内容区。
- 移动端保留紧凑导航，避免遮挡内容。
- 统一登录、加载、未授权状态的视觉表现。

建议改动范围：

- `packages/web/src/components/AppShell.tsx`
- `packages/web/src/components/TelegramLogin.tsx`
- 路由页面对 `AppShell` 的调用处

验收标准：

- 消息、通知、设置、过滤器维护路径均能正常导航。
- 小屏和桌面端布局不重叠、不横向溢出。
- 未授权登录流程仍可正常使用。
- 不改变后端启动链路。

状态：已完成

### Phase 3: 消息页布局与工具栏

目标：

- 优化消息页主从布局，增强过滤器列表和消息列表之间的层级。
- 重构搜索、已读筛选、刷新等工具栏，让高频操作更顺手。
- 移动端继续通过路由切换过滤器列表和消息详情。
- 保留自动定位、加载更早/更新消息、新消息提示等已有行为。

建议改动范围：

- `packages/web/src/pages/MessagesPage/index.tsx`
- `packages/web/src/pages/MessagesPage/components/FilterPanel.tsx`
- `packages/web/src/pages/MessagesPage/components/MessageList.tsx`

验收标准：

- `/messages`、`/messages/all`、`/messages/:filterId` 均能按预期工作。
- 搜索、已读筛选、刷新、返回分组功能不回退。
- 桌面端过滤器列表和消息列表高度正确，滚动区域清晰。
- 移动端可顺畅返回过滤器列表。

状态：已完成

### Phase 4: 消息卡片与消息处理体验

目标：

- 将消息卡片重构为更适合快速处理的 Inbox/Triage 风格。
- 降低默认卡片高度，突出发送者、来源、时间、未读状态和内容摘要。
- 媒体预览、长文本、查看原文等信息在需要时清晰展开。
- 统一搜索命中、锚点定位、未读状态的视觉表达。

建议改动范围：

- `packages/web/src/pages/MessagesPage/components/MessageCard.tsx`
- `packages/web/src/pages/MessagesPage/components/MediaPreview.tsx`
- 必要时调整 `MessageList.tsx`

验收标准：

- 标记已读/恢复未读可用。
- Telegram 原文跳转保留，并继续记录 `telegram_jump_msg_id`。
- 媒体图片、视频、文件、贴纸预览不破版。
- 长文本和极短文本都不会造成布局异常。

状态：未开始

### Phase 5: 过滤器规则编辑器

目标：

- 将过滤器维护页从普通表单升级为更清晰的规则构建体验。
- 优化条件编辑、关键词输入、会话选择、自动定位开关。
- 强化预览面板，让保存前可以更直观看到命中结果。
- 对删除、历史拉取等高影响操作提供明确确认和反馈。

建议改动范围：

- `packages/web/src/pages/FiltersPage/index.tsx`
- `packages/web/src/pages/FiltersPage/FilterForm.tsx`
- `packages/web/src/pages/FiltersPage/ConditionEditor.tsx`
- `packages/web/src/pages/FiltersPage/PreviewPanel.tsx`
- `packages/web/src/pages/FiltersPage/components/*`

验收标准：

- 新建、编辑、保存、删除、启停过滤器正常。
- 预览和历史拉取功能正常。
- 错误信息可以定位到具体操作或字段。
- 过滤器条件数据结构与后端 API 兼容。

状态：未开始

### Phase 6: 全局反馈、空状态与收尾一致性

目标：

- 统一 loading、empty、error、success、confirm 等通用状态。
- 替换页面中的 emoji 图标为 `lucide-react` 图标。
- 统一按钮、badge、输入框、分段控件、列表项的密度和状态。
- 清理阶段性重构留下的重复样式。

建议改动范围：

- `packages/web/src/components/*`
- `packages/web/src/pages/*`
- `packages/web/src/components/ui/*`

验收标准：

- 所有主要页面空数据时都有明确下一步操作。
- 危险操作有确认或足够明显的保护。
- 页面没有明显的 emoji/图标风格混杂。
- 桌面端和移动端关键页面视觉一致。

状态：未开始

## 后续工作流程

每次开始 UI 重构时：

1. 阅读本文档，确认当前阶段和未完成事项。
2. 读取相关页面、组件和目录级 `AGENTS.md` 规则。
3. 只处理一个阶段或一个清晰子目标。
4. 改动前说明将修改的范围。
5. 完成后执行验证命令，并记录结果。
6. 更新本文档中的阶段状态、完成记录和新增决策。

推荐验证命令：

```bash
pnpm build
pnpm db:deploy
```

如果涉及启动链路或需要手动访问界面，补充：

```bash
pnpm start
```

前端开发时默认访问：

- 前端：http://localhost:5173/
- 后端：http://localhost:3000/
